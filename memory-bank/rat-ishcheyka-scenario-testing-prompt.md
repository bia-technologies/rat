# Промпт для продолжения сценарного покрытия РатИщейки

## Задача

Ты работаешь в репозитории `/home/alko/develop/open-source/rat`.

Нужно продолжить покрытие обработки `РатИщейка` сценарными тестами Vanessa Automation для других видов объектов метаданных 1С.

Перед началом обязательно изучи текущую реализацию и уже добавленное покрытие:

- `exts/rat/src/DataProcessors/РатИщейка/`
- `exts/rat/src/CommonModules/РатСборДанныхСлужебный/`
- `exts/rat/src/CommonModules/РатСборДанныхПодпискиНаСобытия/`
- `features_scenario/Ищейка.feature`
- шаги RAT для Vanessa Automation:
  - `exts/rat/src/DataProcessors/РатШагиVA/Forms/Форма/Module.bsl`
  - `exts/rat/src/DataProcessors/РатШагиVA/Templates/ЭкспортныеШаги/Template.txt`
  - `exts/rat/src/CommonModules/РатВзаимодействиеСКлиентомТестированияКлиент/Module.bsl`
  - `exts/rat/src/CommonModules/РатВзаимодействиеСКлиентомТестированияВызовСервера/Module.bsl`

## Обязательный порядок работы

1. Сначала определи по коду, какие типы объектов реально поддерживаются сбором данных и подписками `РатИщейки`.
2. Для каждого кандидата найди стабильный способ создать исходные данные и выполнить изменение через UI/VA.
3. Используй существующие шаги RAT с внешней системой `ЭтаБаза` для подготовки данных, если они подходят.
4. Само изменение, которое должно попасть в сбор данных, выполняй в сеансе клиента тестирования:
   - клиентский код: `И я выполняю алгоритм в клиенте тестирования`;
   - серверный код в сеансе клиента тестирования: `И я выполняю алгоритм в клиенте тестирования на сервере`.
5. Не придумывай поведение обработки. Проверяй только реальные пользовательские сценарии: открыть Ищейку, старт слежения, изменение объекта, остановка слежения, список объектов, выбор строки, отображение сравнения.
6. Разделяй сценарии по feature-файлам, а не собирай один огромный `Ищейка.feature`.
   Существующий `features_scenario/Ищейка.feature` оставь как базовое покрытие, а новые виды объектов выноси в отдельные файлы в том же стиле, например `Ищейка - Документы.feature` или `Ищейка - Регистры сведений.feature`.
7. Добавляй минимальный набор сценариев. Не расширяй общие библиотеки и форму Ищейки без необходимости.
8. Запускай только релевантные сценарии:

```bash
v8-runner test va --feature "<имя нового feature-файла без расширения>" --clean-before-execution
```

При необходимости используй `--scenario-filter` для одного нового сценария.

Перед финальным ответом выполни:

```bash
git diff --check
git status --short --branch
```

Если изменения коммитятся, учитывай, что precommit4onec может синхронизировать `documentation/docs/functionality/ЭкспортируемыеШаги.md` из `Template.txt`.

## Кандидаты для следующего покрытия

Выбирай только те типы, которые стабильно воспроизводимы в тестовой конфигурации и реально попадают в подписки записи:

- документ: создание через `ЭтаБаза`, изменение реквизита или табличной части в сеансе клиента тестирования;
- план видов характеристик;
- план счетов;
- план видов расчета;
- план обмена;
- независимый регистр сведений;
- бизнес-процесс;
- задача.

Для каждого типа сначала проверь метаданные тестовой конфигурации и существующие features, чтобы не угадывать имена объектов и реквизитов.

## Подводные камни из предыдущего покрытия

1. Изменение должно выполняться в том же сеансе, где включено слежение.
   Изменение через `ЭтаБаза` из процесса менеджера VA не попадает в сбор `РатИщейки`, потому что временный контекст слежения хранится в параметрах сеанса.

2. Для серверных объектов (`Справочники`, `Константы`, менеджеры метаданных) нужен шаг `И я выполняю алгоритм в клиенте тестирования на сервере`.
   Обычный клиентский контекст тонкого клиента не видит серверные глобальные менеджеры и даст ошибку вроде `Variable is not defined (Справочники)`.

3. Не проверяй HTML-поле `СравнениеВерсий` стандартным шагом `значение поля содержит текст`.
   Такой шаг пытается передать наружу весь HTML/JS diff-viewer и может падать в Vanessa/XDTO на недопустимом символе в JS-бандле.

4. Для проверки сравнения используй специализированный шаг:

```gherkin
И сравнение версий Ищейки в клиенте тестирования содержит текст "ОжидаемыйТекст"
```

Он выполняет проверку внутри клиента тестирования и возвращает только булево значение.

5. После нажатия `ФормаЗавершитьСлежение` форма сама вызывает `ОтобразитьСравнениеВерсий()`.
   Сценарий должен проверять появление сравнения без закрытия и повторного открытия формы.

6. Таблица `Объекты` в UI не обязана иметь все реквизиты строки как видимые колонки.
   Например, колонка `Ключ` есть в данных формы, но не доступна стандартным табличным VA-шагам. Используй пользовательски видимые колонки, например `Представление`.

7. Для справочников коды должны быть уникальными.
   Не используй фиксированные значения вроде `ИЩ001`; генерируй уникальные коды через `Новый УникальныйИдентификатор`.

8. В сценарии константы исходное значение лучше выставлять до старта слежения, а новое значение менять после старта.
   Так сравнение показывает переход от старого значения к новому.

9. Если добавляешь или меняешь экспортируемые VA-шаги, обновляй `Template.txt`.
   При коммите hook синхронизирует производный файл `documentation/docs/functionality/ЭкспортируемыеШаги.md`.

10. Первый прогон может падать на ошибках автоматизации, не на логике Ищейки.
    Исправляй только то, что относится к текущему сценарию и текущему виду объекта.

## Формат итогового отчета

В финальном ответе используй структуру:

- Analysis: какие типы объектов проверены по коду и почему выбраны.
- Planning: какие сценарии добавлены и как проверяются.
- Implementation: какие файлы изменены.
- Testing: команды и результаты.
- Review: риски, ограничения, findings reviewer-а.
